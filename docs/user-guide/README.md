# 作者上手指南

先用仓库里的小样例确认环境能运行，再用一个独立的 MZ 工程做自己的游戏。不要在正在制作的正式工程或含真实玩家存档的目录里试装。

## 1. 运行开发样例

按[项目首页](../../README.md)下载仓库并执行引导命令。脚本从你本机的 RPG Maker MZ 安装准备基础素材，准备固定版本的 RPGReactor、Showdown 及框架构建产物。如果 MZ 不在 Steam 的默认目录，在执行时用 `MZ_APP` 指向你自己的 `RPGMZ.app`。需要核对版本或分步安装时，查[环境指南](../PROJECT-GUIDE.md#环境与构建)。

在 MZ 打开框架根目录的 `game.rmmzproject` 并点击「测试游戏」。选择「新游戏」后：

1. 和起点附近的初始队伍事件对话。再触发一次，确认不会重复领到同一份成员和道具。
2. 到左侧草丛走动，尝试野生战斗。返回地图后，可以和治疗事件互动。
3. 打开队伍菜单，检查成员状态。用普通存档功能保存，再从标题继续。

在编辑器里可以打开起始地图（文件 `data/Map005.json`），查看这些示例使用了哪些原生事件和插件命令。素材和地图只用于开发示范，不是正式 Demo。

## 2. 新建自己的工程

在 MZ 新建工程，并用它的副本试装。让框架工具检出、作者工程和内容暂存目录互不嵌套。继续用 MZ 编辑自己的地图、事件、菜单和工程数据库；不要整体复制样例的 `data/` 或 `js/` 覆盖现有工程。

在副本中接入同一框架检出构建的运行时，按[完整安装清单](integration.md#从新建-mz-工程接入)处理：

1. 用固定 RPGReactor 的运行时和加载入口接管 MZ 宿主，保留作者工程的插件清单，不混装不同版本的核心文件。
2. 放入同一构建的框架生产文件、指定插件及固定 Showdown 运行时。按清单顺序启用插件，不启用 Smoke、FlowTest 或样例演示插件；不要用测试插件来初始化玩家队伍。
3. 在 `PS_World` 配置战败返回的位置，例如 `CharacterHome` 或 `GlobalHome`。用编辑器核对地图、坐标、方向，以及是否需要配置起始回程开关。

在替换入口和基础素材前，确认文件的来源与使用条件。遇到同路径但不同内容的素材，不要覆盖；先在工程副本中解决冲突。

## 3. 编译和安装作者内容

参考 [`content/sample/`](../../content/sample/) 的文件结构，在单独的目录编写自己的内容。基础文件为 `manifest.json`、`sources.json`、`species.json` 和 `overlays.json`。在 `manifest.json` 设置自己的 `id`，在 `sources.json` 记录数据与资源来源。要配置初始领取和训练家战，参照样例增加对应的领取、训练家和训练家类型数据。

在**已经构建完成的框架根目录**执行，把下面的路径和内容 ID 改成自己的。所有路径都用绝对路径；暂存目录必须不存在，其父目录必须已经存在。

```bash
node scripts/author-content.cjs \
  --src="/absolute/author-content" \
  --stage="/absolute/work/first-author-build" \
  --expect-id="my-content-id" \
  --game="/absolute/MZ-author-project"
```

只想检查和编译时，去掉 `--game`。成功后，暂存目录会有 `content.json` 和 `inventory.json`；命令末行会报告内容 ID 与文件摘要。带上 `--game` 才安装到指定工程的 `data/framework/content.json`，已有文件不会被替换。重新安装时，先在工程副本中备份旧文件、腾出安装位置，再选一个新的暂存目录。

不要用默认的 `content:build` 更新作者内容，它默认构建框架样例。也不要只看 `content:check` 的退出码就认定安装的是想要的版本；核对作者工具报告的内容 ID 与实际文件。

[菜单、帮助与训练家卡](menus.md) · [地图和旅行](world.md) · [插件命令速查](commands.md)。

## 4. 做出第一条剧情流程

在 MZ 的事件页里选择「插件命令」。建议先用以下几个命令连出一个最小流程，再加入剧情、美术和可选内容。

| 目标 | 怎么接 |
| --- | --- |
| 领取初始队伍 | 用 `PS_BattleFlow → ClaimGrant`，填内容中的领取 ID，选一个专用 MZ 结果变量。首次成功是 `1`，重复领取是 `2`。 |
| 发起训练家战 | 用 `PS_BattleFlow → StartTrainerBattle`，填内容中的训练家 ID 和版本。先清空专用结果变量，等战斗事件恢复后再判断，只在胜利结果为 `1` 时发放奖励。 |
| 用徽章拦住入口 | 获胜后用 `PS_Inventory → SetBadge` 发章。门口事件用 `QueryBadge` 查询**指定索引**，先清旧值，然后只允许结果为布尔值 `true` 时通过。留空索引查询的是数量，不是持有状态。 |
| 对话和选择 | 用 `PS_Management → ShowMessage`、`ShowChoices`；按需要填写中英文文本及保存结果的变量。完整参数查[命令参考](commands.md)。 |

若要单独验证手动档，先在工程副本中关闭自动存档，再用测试档验证保存、退到标题和继续读档，核对队伍、徽章和领取状态。要验收自动存档时，再开启该选项并单独检查槽 0；在新进程里明确选择要验证的档位。不要带入真实玩家存档。

## 5. 验证与打包

- 改动框架前，按[开发者指南](../PROJECT-GUIDE.md)做环境检查。准备好依赖后，可在框架根目录运行 `PF_NO_SKIP=1 ./scripts/test-headless.sh --scope=regular` 做常规自动回归。它不会打开 MZ/NW.js。
- 普通「测试游戏」适合体验作者工程，不授予框架内部测试权限。不要依赖旧 Mac 测试入口或旧测试参数隔离存档。独立测试边界见[接入清单](integration.md)，常见错误码见[诊断说明](diagnostics.md)。
- 如需试做 Mac 本地包，[开发者指南的打包说明](../PROJECT-GUIDE.md#环境与构建)针对框架样例检出；不能把它当作自己的作者工程安装或发布工具。对外发布前，分别核对代码、运行时及素材的[来源与分发条件](../sdk/distribution-notices.md)，另做签名、公证和下载后验收。
