# 存档版本、迁移、恢复与防重复账本（第三步 B3）

范围：**战斗外**的持久游戏状态（队伍、盒子、背包、金钱、图鉴、`appliedBattles`）。战斗中途存档不在范围内（引擎快照往返可行，但战中续玩的事务一致性没有验证）。代码：`src/framework/rules/save-schema.ts`（纯函数）、`rules/state.ts`、`tools/save-store.ts`（Node 单文件存储）、`src/plugins/PS_SaveState.ts`（MZ 存档入口）。测试：`experiments/step3/test-save.cjs`，游戏内场景 T9。

## 1. 版本

状态文档的 `schema` 与战斗协议版本（`protocol-v1.md`，目前仍是 1）是两回事。

| schema | 来源 | 与当前的差别 |
|---|---|---|
| 1 | 第二步原型（含 `step2-closed`） | 成员可能没有 `statusCount`；被击成剧毒的成员可能存成 `status: "tox"` |
| 2 | 第三步 | 成员带 `statusCount`（睡眠=剩余回合，中毒=0）；中毒存为普通 `psn`（WP20/WP39：战后中毒计数清零） |
| **3（当前）** | 第四步 | 加 `claims`（一次性领取凭证：领取 ID → `{kind:"grant"}`）；2→3 只加空凭证账本。见 `docs/step4/README.md` |

**声明支持的旧版本：1、2（第四步起）。** 夹具：`experiments/step3/fixtures/legacy-v1-flow-state.json`（`step2-closed` 时在真实 MZ 运行里捕获的状态）；最老形态（没有 `statusCount`、有 `tox` 和睡眠成员）由测试从它构造。不支持任何其他版本，也不支持“猜”。

## 2. 迁移与错误（`migrateGame`）

- 在**副本**上迁移，输入文档从不被改动；迁移后再做严格校验（`validateGame`：字段类型与范围、未知字段、重复成员 id、背包/金钱/图鉴/账本的形状）。
- 睡眠成员在 schema 1 里没有计数：**不编造数字**，保持缺省并在 `notes` 里说明，下次战斗开始时由引擎重新抽一个睡眠时长（旧行为）。
- 失败一律给出带编码的诊断，**不重置、不清空、不覆盖**：
  - `corrupt`：不是对象、没有 schema、文件读不出 JSON；
  - `unknown-version`：schema 比本版本新（“Nothing was changed”）、为 0/负数/小数/字符串、或不在支持列表里；
  - `invalid`：结构校验失败，带每一处的路径（含**战斗临时字段**如 `boosts`、`volatiles`、`activeNow`——它们不属于存档，出现即拒绝）。
- `applyBattleResult` 拒绝对非当前 schema 的状态写入（先迁移）。

## 3. 存储边界（明确声明什么被证明了）

| 层 | 声明 | 证据 |
|---|---|---|
| Node 单文件 `SaveStore` | 写临时文件 → fsync → 重命名。任何抛错**或真实进程被杀**发生在 6 个点（`start`、`afterBackup`、`beforeSave`、`afterTmpWrite`、`beforeRename`、`afterRename`）时，磁盘上是完整的旧文件或完整的新文件，两者都读得出；遗留临时文件在读取时丢弃；重试后结果只生效一次。升级旧文件前，把原文件原样复制为 `<file>.v1.bak`（先写临时再重命名）。读不懂的存档（损坏、更新版本、无效）**不会被覆盖**，只抛 `SaveError`。 | `test-save.cjs`：模拟抛错与真实 SIGKILL 分别记账；`test-writeback.cjs`（第二步已有）。 |
| MZ 存档（`$gameSystem._psGame`） | 载入：迁移成功则替换，失败则**原文档保持原样**并记 `_psSaveError`，此后战斗拒绝开始（`PSFlow.game()` 抛错、场景中止并说明原因），不会在不可用状态上继续或用战斗结果覆盖它。存档前：先校验；失败只记 `_psSaveWarning` 并仍然存（拒存会丢进度，警告就是诊断）。 | 游戏内场景 T9（MZ 自己的 `saveGame/loadGame`：schema 1 迁移；schema 9 与损坏文档被拒且逐字保留；战斗拒绝并说明原因）；V1（重启后读档一致）。 |
| **没有声明的** | MZ 存档文件本身的原子性/断电耐久是 **MZ 的**，本步没有检查；战斗中途存档；多文件存档；跨设备同步。 | — |

## 4. `appliedBattles`（防重复账本）：策略与理由

**身份**：`(battleId, resultHash)`。同 id 同内容 = 重放，什么都不做（`already-applied`）；同 id 不同内容 = 拒绝（防篡改/防“同一场战斗给出另一个结果”）。

**有效窗口**：没有窗口——一个结果在**同一份存档时间线上**最多生效一次，不论过了多久、中间提交了多少别的结果。

**持久边界**：账本和被它保护的状态在**同一个文档**里（同一次 MZ 存档/同一次文件替换）。读旧存档会把账本和状态一起回滚，所以“恢复后重试”会合法地再生效一次，且只一次；不存在“状态回滚了但账本没回滚”的撕裂。

**增长**：线性，约 95 字节/条（实测：10,000 条 = 948,891 字节 JSON；`ledgerStats(state)` 可随时读出）。按一个很长的游戏进程每场战斗一条估算，几千到一万条是 0.5–1 MB 量级，MZ 存档会压缩。**本步决定：保留全部身份，不截断、不压缩**。

**为什么不做水位线压缩**（“序号 ≤ N 的战斗都已结算”，低于水位线的旧结果被协议拒绝）：战斗 id 里的序号只是插件的约定，协议里的 `battleId` 只是字符串；序号单调递增并不蕴含“小于 N 的战斗都已结算”（取消、失败、未完成提交都会留下空洞），读旧存档后序号也可能重用。要采用它，需要先证明：水位线不会跨过仍可能提交的空洞；存档身份、恢复与序号分配不会碰撞；乱序、重复、取消、恢复后重试都不多发不漏发。这些前提目前**没有成立也没有证明**，所以不采用。若将来账本大到成为问题，路径是：先让游戏层发放有序的、写进状态的战斗令牌（协议的加性变更），再按上面三条做证明与测试，最后才压缩；在那之前由 `ledgerStats` 让增长保持可见。

**已测试的不变量**（`test-save.cjs`）：500 场之后重放最老的结果仍是 no-op，同 id 改内容被拒；乱序提交（B 先于 A）各生效一次；没有产生结果的战斗不留痕迹也不占用 id；还原旧存档后重试恰好生效一次；增长曲线线性。
