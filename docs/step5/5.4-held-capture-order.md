# Capture party recovery priority

Status: local repair candidate; independent review and integration acceptance pending.
Baseline: `3b2f1568d054aead18571ae0af048705783fb416`.

## Confirmed defect

An actual App → Session → pinned Gen8 battle transfers B's Leftovers to an empty wild opponent with Trick, then from that opponent to initially empty A with Trick. Both original players remain in the party when the opponent is captured.

With the original roster A/B, A's empty recovery immediately falls back to its current token before B can claim its own live recovery. A keeps Leftovers and B gets nothing. Reversing the roster to B/A restores Leftovers to B. Both outcomes conserve quantity, so count-only tests miss the incorrect ownership.

The existing capture contract in `5.4-held-capture-conservation.md` already gives player preferred recovery precedence over current fallback. This repair applies that precedence across all player claims instead of completing preference plus fallback one member at a time.

## Minimal repair

1. Claim every existing player's preferred field, using party recovery or boxed current exactly as before.
2. Only then try current fallback for the remaining empty player slots.
3. Continue the existing captured-member claims and remaining-current conservation fill unchanged.

No tracker, battle-time Trick behavior, item-source identity, protocol, save schema, atomic install, or no-capture writeback contract changes.

## Tests and scope

Thirty new tests use both roster orders and assert ownership as well as count:

- 12 pure-rule cases: B → wild → A and B → wild → C → wild → A; distinct and equal-name source items; captured member enters party or box.
- 18 actual App/Gen8 cases: the same chains and both orders; capture into party, full-party capture into a box, or replacement of an unrelated unused member. Pending reception is zero-write, followed by one install and exact replay.
- Debug engine access only observes active identity and pre-capture items. It does not seed state, invoke item primitives, or manufacture journal events in the actual App cases.

The old implementation with these tests has 9 App failures / 9 passes and 6 pure-rule failures / 6 passes. The complete focused suites after repair pass 59 App and 36 pure-rule tests. Ten related held-item suites pass 221/221, with no failures, cancellations, or skips. Exact logs and subsequent aggregate results are stored outside this repository beside the isolated repair worktree.

## Deliberately open contract boundary

These new recovery-priority assertions keep all transfer-chain participants in the party. Replacing an unrelated unused player additionally checks that the receiving plan does not change that guarantee.

If a transfer-chain participant is itself boxed, its explicitly specified preferred current field can compete with another remaining player's preferred recovery for the same source token. The existing documents do not define priority between those two preferred claims. This repair leaves that competing-preference behavior unchanged and does not claim order independence for it. Defining that rule requires a separate contract decision, not an assumption in this fix.

This is synthetic product testing, not original Ruby comparison, NW.js/manual validation, CI, or full 5.4 acceptance. No push or merge is part of this task.
