# 5.4 捕获持物来源守恒整改

状态：修复候选，待独立审查与整合验收。基线 `6ca8fb74037bb0de9d1b1cf03d1f4f8c2bf2dc6d`。

## 问题与决策

旧写回把仍在队伍的玩家成员恢复项 I 与被捕成员当前项 C 分别安装。
玩家用 Trick / Bestow 把 X 交给野生目标再捕获时，同一来源物会出现两份。
双方原有 X/Y 时还会变成 X/X，丢掉 Y。旧 App 测试把复制当成预期，不能证明正确。

本整改不修改 Showdown 战中规则。保留玩家战后恢复的优先语义，但捕获接收时必须按**物品实例来源**守恒：

- 每个开战成员的初始持物创建一个独立 token。同名道具也不是同一个 token。
- 依据可信完整 journal 的 donor `sourceId` 重放转移；不能靠道具名猜来源。
- 消费/永久损失退休该 token；Recycle、Harvest、Pickup 恢复原 token，不新造一份。
- 仍在队伍的玩家先领取存活恢复项，已被接收决定换入盒的玩家仍优先当前项。
- 捕获项 C 若已经被玩家恢复领取，则不能复制；改取其仍存活、未被领取的恢复项。
  因此 X/Y 双持互换后捕获，玩家恢复 X，被捕成员保留 Y。
- 若玩家原物真的已消费，其仍持有且无人领取的交换所得可以保留；不为恢复一个已消耗实例而丢掉另一件存活物。
- 捕获的空 C 不会自动恢复被打落的野生物；但若其原物仍被另一成员实际持有且未领取，可以归还该交换物。
- 无来源可证明时拒绝本次安装，不以同名碰撞猜测、静默复制或吞物。

这明确解决原合同未规定的捕获恢复冲突，不改变未发生捕获时的既有写回；不修改冻结 BattleResult v1、RequiredFacts v1、持久存档 schema 或引擎来源协议。
事实校验、来源认证、pending 接收、单次安装、重复 finish 和 abort 仍由原应用事务负责。
来源 token 只在纯规则计划中派生，不作为调用者可提供的权限字段。

## 独立 Ultra 首审与 R2

首候选 `ce6a018`：**REQUIRES_CHANGES**。虽然主三套 84 项通过，独立实际引擎探针在 9 项中发现 4 项失败。
两玩家连续 Trick（P1 X、P2 Y、野生空手或 Z）后，捕获替换 P1/P2，单次优先领取仍可能把存活来源物挤掉。
同名实例也可能从两份变一份；因此首候选不得接受。原报告、探针与失败日志保留。

R2 在所有优先领取完成后进行第二阶段闭环：
- 只收集本次实际安装的玩家及被捕来源成员中，仍存活、仍实际 current 持有且尚未领取的 token。
- 按稳定来源 ID 排列 token，按稳定目标 ID 排列空持物槽，逐个补齐；不依赖对象键或接收决策的枚举顺序。
- 来源去重依据 token 身份，不按物品名；不收集未捕获对手、recycle-only 或已打落而无 current 的野生恢复项。
- boxed C、party I 是第一阶段优先项，不授权后续吞掉整个链条剩余的物品。多节点链冲突时允许第二阶段填补其他空位，保持玩家总资源。
- 若仍存活未领取物品多于空槽，明确拒绝整个安装，不静默丢弃。

新增真实引擎三节点链（异名/同名）×入队、入盒、替换 P1、替换 P2；新增真实 App 两玩家→空手野生链的同名/异名四去向。
R2 主三套为 94 项（facts 24、engine 29、App 41），作者重跑旧独审 9 项均通过；这不是独立复审结论。
