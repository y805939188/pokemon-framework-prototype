# 2.2 — RPG action extension: contracts, route, evidence

Status: **early feasibility result for the user (not yet a C-decision).** Branch `step2/2.2-rpg-actions`. All results below are from runs in this repo; "spec vector" means an expected value derived in the clean-room test catalog, not Ruby-executed output.

## 1. Decisive contracts extracted (own words; sources are clean-room specs only)

| Area | Contract carried into the experiment | Spec |
|---|---|---|
| Turn order | Within the action phase: calls → switches → **items (incl. balls)** → mega → moves. Item/ball/run each consume the whole action of that seat. | WP40 §5.1 |
| Item registration | Usable-in-battle type 1..5; consumable is deducted **at registration**; cancelling before the turn returns it; at execution a re-check runs: failure → "no effect", the consumed identity stays and refund rules apply (not automatic for balls). | WP40 §4.2, WP28 §3.5 |
| Heal table | POTION 20, SUPER 60, HYPER 120, MAX = missing, etc. Actual = min(request, missing HP). Fainted or full HP → no effect. | WP28 §5.1 |
| Ball | Refused without consuming if: party+boxes full, balls disabled, not first action, half-invulnerable target, >1 living foe (except snag). Thrown ball is spent whatever happens. Trainer battle blocks the ball. | WP38 §2 |
| Capture math | m=((3A−2B)·rate)/(3A) kept as float, status ×2.5 (sleep/freeze) or ×1.5, single floor at the end, min 1; x≥255 or Master → certain; y=⌊65536/(255/x)^0.1875⌋; critical gate (owned-count tiers, charm ×2) then one roll; else up to 4 rolls, first failure stops. | WP38 §3 |
| Capture success | Wild last foe → decision "caught" (4); then growth/exp, party move, ownership/ball write, receiving policy. Ball effects (heal, friendship) on success. | WP38 §5–6 |
| Run | Wild only. Guards: trainer, can't-run, deterministic escapes, trapping. Rate = 256 if faster else ⌊own·128/foe⌋+30·attempts (speeds unmodified, attempts counted only when the calculation is reached). Success = decision "run" (3); fail consumes the action. | WP41 §7 |
| Growth timing | Exp is paid right after a KO (capture too); level-up recalculates stats and HP (max-HP delta added), moves are learned, and the next action/request uses new values; a step in the same turn is not an end of battle. | WP42 §4 |

## 2. Probes and route comparison

**Mid-battle level-up probe — PASS** (`experiments/step2/s2/probe-levelup.cjs`): setting the level with Showdown's own primitives (`spreadModify`, `updateMaxHp`) + re-issuing requests gives new stats/details in the next request; the next turn's log is **identical** to a control battle where the Pokémon was created at the new level with the same seed (and the speed order flips as expected); HP rises by the max-HP delta; the snapshot restores level/stats. Limit: the bridge applies it between turns. For a KO mid-turn in doubles, a later ally action of the same turn would not see the new stats; an in-engine hook (e.g. a format `onFaint`) can close that gap if the spec requires it (not tested).

**Existing extension points checked:** Showdown loads `dist/config/custom-formats.js` (merged into the format list), formats can define event handlers, `Battle.runEvent` accepts arbitrary event names, the queue accepts an `'event'` action with a priority, and any JSON-able extra property on the battle object is serialized into `toJSON()`.

| Route | What it is | Result |
|---|---|---|
| **C (chosen)** engine event action | Gateway queues `{choice:'event', event:'RpgAction', priority:99}`; payload parked in `battle.rpg.pending`; the custom format's `onRpgAction` resolves item/ball/run inside the turn using `battle.random`. No Showdown source change; only a file added at stage time. | Order is exactly switches → items → moves; cancel before commit just drops the payload; snapshot with a parked action resumes identically; PRNG draws reproducible. |
| A (rejected) bridge pre-mutates state + `pass` | Effect applied before the turn is committed. | Measured: item resolves **before** an opponent's switch (violates WP40 order) and mutates HP before commit, so cancel/undo needs rollback. |
| Placeholder move (not built) | A fake move that carries the action. | Rejected by code reading, **not tested**: it would inherit move side effects (Choice lock, last-move records, Disable/Encore/Taunt/PP) which items must not have. |
| External settlement | Not needed. | Not evaluated. |

## 3. Results (what ran)

`node --test experiments/step2/s2/test-actions.cjs` — 11/11 pass; also `probe-levelup`, `probe-heal`, `probe-route-compare`, `test-headless` (now 5 checks incl. `rpg-actions`), and the same 5 checks pass inside NW.js 0.117.0 (`evidence/nwjs-direct-2.2.json`).

- Capture/escape math matches the spec vectors CP01–CP05, CP07, CP10, CP06, CP08, CP13, CP14, CP24 and the escape formula (derived expectations).
- **S2** Master Ball → end reason `caught`, foe never acts, outcome carries the stable id and current HP/status; engine winner stays `null` (the engine tie is not the business meaning).
- **S3** failed throw: shakes recorded, foe acts, next request issued. 1,500 seeded engine battles: success count within 4.5σ of the closed form.
- **S4/S5/S6** run: faster → rate 256, no foe action; slower → rates equal `⌊own·128/foe⌋+30·attempt` per attempt, foe acts only after failures, eventually escapes; trainer / trapped / balls disabled / multiple foes are refused (menu query) or denied in-turn without ending the battle.
- **S7** Potion family (cap at missing HP, no-effect on full/fainted/unknown), status cures (wrong status = no effect), X Attack (+2, capped), bench vs active differences, cancel before commit, snapshot with parked action.

## 4. Limits and open questions

1. Singles only (`gateway.act` uses the first active slot); doubles (S10) belong to 2.3.
2. Showdown has no catch rate, ball names or owned-species data; the game must pass `catchRate` and context (`ownedCount`, area flags) in the payload. Ball set implemented: ~20 of 26, no Safari/Bug-contest/Snag/Shadow paths.
3. Business ledger (deduct at registration, refund on cancel/no-effect, ball never refunded) is **not** in the engine; it belongs to the 2.3 write-back contract. The engine only reports `ok/noeffect/invalid/blocked/notarget/escaped/caught`.
4. Capture success here only ends the battle with a hand-over record; exp on capture, party removal, ownership and receive policy are 2.3.
5. X-item stage amount (+2) and the confusion handling of Full Heal follow common convention; WP28 §5.5 should be checked before freezing.
6. Spec leaves open whether the old "refunded but identity kept" anomaly (WP40 §4.2.1) is to be preserved; unresolved here.
7. Run is resolved in the turn queue rather than "on the spot at selection" as the spec phrases it; in wild singles the observable result is the same (wild foes cannot switch). Re-check for doubles.
8. Golden results are engine regression baselines, not rule-verified against the Ruby reference.
