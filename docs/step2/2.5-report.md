**Same inputs, same outcome across hosts:** for S1–S10 the fixed-input fingerprint (normalized events, requests, end reasons, results) computed in the package under Node 26.7.0 equals the one from plain Node 22.21.1 — all ten identical (`evidence/package/ps-matrix-*.json`). The in-game flow T1–T7 + V1 (real keys, real map events, real MZ save/load, process restart) pass in the package; the host path in the report is inside `PokemonFrameworkPrototype.app`.

Stability: before the fix, 4 of my 10 package-suite runs failed (a T5 timeout, T1 cascades). Cause found with diagnostics: **the game window loses OS focus for stretches during automated runs (blur at frame 94 for ~800 frames) and a blurred window ignores input and is throttled.** The driver now takes focus back before every key press and confirms that OK had an effect; after the fix both full package-suite runs I made passed (flow T1–T7 + V1 + matrix, exit 0), and in the final measurement launches no blur occurred. Two full runs is a small sample: treat the suite as stable-looking, not proven flake-free; it also needs the window to be allowed to take focus.

Not covered (not claimed): defeat/draw, real process-kill inside the package (the SIGKILL durability test is Node-only), multi-target throws, mega/dynamax, doubles UI, Windows/Intel.

## 3. Measurements (3 separate launches, window focused, no message pacing)

Method: the launching shell passes its epoch time; timings use the renderer's `performance.now()`/`Date.now()`; per-action times wrap the session call; frame times are `SceneManager.update` deltas; memory is `process.memoryUsage()` plus the summed RSS of all app processes (`ps`). Raw runs: `evidence/package/perf/run*.json`, summary `perf-summary.json`.

| Metric | Median (range of 3) |
|---|---|
| Cold start, launch → plugins loaded | 821 ms (792–832) |
| Cold start, launch → map ready | 1,850 ms (1,831–1,869) |
| Engine modules load (first battle only) | 2.1 ms |
| First battle: session create / event start → first menu | 160 ms / 550 ms |
| Later battles: session create / event start → first menu | 2.1 ms / 133 ms (worst 134 ms) |
| Action latency p50 (engine turn incl. foe + growth): move / item / ball / run | 3.4 / 3.4 / 2.4 / 1.8 ms (max 10.2 / 5.5 / 3.5 / 4.8) |
| Frames in the battle scene: p50 / p95 / max | 16.7 / 18.6 / 177 ms; one frame >100 ms per run (the scene-creation frame) |
| Frames on the map: p95 / max | 18.6 / 77 ms |
| App RSS: map ready → 4 → 12 → 24 battles | 1,207 → 1,307 → 1,334 → 1,371 MB |
| JS heap (renderer): 4 vs 24 battles | 36 vs 36 MB |

Notes: (a) the very first launch after building a package was slower and variable in earlier trial runs (6 s and 26 s to plugins loaded; steady-state ≈0.8 s) — consistent with a macOS first-run check of a new ad-hoc-signed bundle, not diagnosed. (b) Numbers are for this machine and a fast scripted path; they are not a general performance claim, and the placeholder UI has no art or animation.

**Memory growth (found, bisected, not fixed):** app RSS grows ≈1.7–4 MB per battle with no plateau over 100 battles (1,216 → 1,610 MB), also with forced GC. Bisect with forced GC: the engine/session layer does **not** leak (Node, 100 battles: heap 43 MB and RSS 169 MB flat); the growth is in scene open/close in this runtime — a bare Scene_MenuBase with three windows and no engine leaks ≈2.5 MB RSS per open/close, Scene_Base with three windows ≈1.7 MB, MenuBase with no windows ≈0.7 MB; explicitly destroying window canvases cuts it to ≈1.45 MB (applied in `Scene_PSBattle.terminate`). The remainder is outside this plugin (Reactor/Pixi scene lifecycle). At ≈2 MB/battle a long play session of thousands of encounters would be a real problem → C2 risk #1.

> **Update (runtime-issues pass):** the memory growth found here is fixed (two upstream bugs, `PS_RuntimeFixes`), saves no longer live inside the bundle (`PS_SaveLocation`), and a signing plan with a hardened-runtime proof exists — see `runtime-issues.md` and `signing-plan.md`. The per-battle RSS figures above are the *before* numbers.

## 5. C2 — for your decision

**Exit-criteria check (handoff §7):** actual package passes the defined matrix ✔; extension route has evidence ✔ (2.2 report); state ownership, write-back and minimal consistency boundary defined ✔ (protocol doc; atomicity claimed only for the single-file store, MZ save durability is MZ's); duplicate submission does not duplicate consumption/rewards ✔; key doubles combinations have evidence ✔ (engine/session level); protocol v1 frozen for the validated scope ✔. **Open items that keep this from being unconditional:** memory growth per scene (runtime issue), save location inside the bundle, first-launch slowness, no Developer ID/notarization, macOS-arm64 only.

**Technical conclusion:** the route is feasible. Showdown can run inside the MZ/Reactor runtime (NW.js 0.117), RPG actions, growth and write-back work with a thin, tested bridge and zero Showdown source patches, and the same inputs give the same outcomes in Node and in the packaged app.

**Decisions I need from you**
1. **Continue on this route?** Recommendation: yes.
2. **First-version scope.** Recommended cut: singles in the first version; doubles at the rule/engine level kept (tests exist) but the doubles UI as a later batch; "long tail" (Safari/Snag/Shadow, recordings, battle-time save, mega/dynamax, non-Gen-8 rules) as separate later phases each with its own spec check.
3. **Runtime issues to resolve before building UI at scale:** (a) the scene memory growth — fix upstream in RPGReactor or reuse one persistent battle scene; (b) where saves live in a packaged app (user data dir vs bundle); (c) first-launch behaviour/signing plan (Developer ID + notarization when you want to distribute).
4. **Platforms:** macOS-arm64 is verified. Windows (incl. how the project is packaged there) and Intel Mac are untested; keep in scope or defer?
5. **Reference quirks** are recorded in `deviations.md`; four decided, none new from 2.5.

**Rough effort outlook (not measured; depends on 2–4):** the bridge pattern is proven, so each function family is mostly content data + rule porting + UI + tests.
