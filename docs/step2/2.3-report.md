## 2. Decisions needed from you (reference behaviour vs. what we implemented)

*All four were decided on 2026-10-18; the outcome is in `deviations.md` #1–#4. The text below is the question as asked.*

1. **Refund anomaly (WP40 §4.2.1 / WP42 §6.0):** the reference refunds a failed item at execution but keeps its consumed-identity, so normal end-of-battle can refund again (item count can end higher). We implemented *refund once*. Keep that, or reproduce the reference quirk?
2. **Fainted member revival on level-up (WP19 5.5):** reference revives a 0-HP member when max HP grows. Our game-rule function reproduces it, the engine does not (stays 0); fainted members do not receive exp anyway, so it only matters for future level-setting items. Keep or drop?
3. **Held item restore at battle end (WP42 §6):** not implemented; `item` is outside the write set. Decide the restore policy before items/berries are in scope.
4. **Exp timing:** default is after the turn (equal to the reference in singles; differs in doubles only when a later same-turn action of a participant depends on the new level). The faint hook can make it exact if you want that fidelity.

## 3. C1 — route evidence, cost, risks, estimate

**Route (carried from 2.2, extended here):** custom Showdown format + engine `event` action for RPG actions; game-rule layer (growth, ledger, write-back) outside the engine; engine told the outcome and cross-checked. Evidence is the passing suites above, the same six checks inside NW.js, route comparison in the 2.2 report.

**Patch / maintenance footprint**
- Showdown source patches: **0**. One overlay at stage time: `dist/config/custom-formats.js` (+ `rpg-rules.cjs`), a Showdown-supported extension point.
- Our code: engine bridge ≈ 1,570 lines (gateway 355, session 363, growth 148, state 91, store 50, formats 160, rules 146, harness 236, content 21), tests/probes ≈ 1,050 lines.
- Showdown internals we rely on beyond its documented API (the real upgrade risk). *(corrected: the first list was incomplete.)* Choice machinery: `Side.choice.actions`, `chooseMove`, `chooseSwitch`, `getChoiceIndex`, `clearChoice`, `isChoiceDone`, `emitRequest`, `Side.activeRequest`; `Battle.choose`, `commitChoices`, `allChoicesDone`, `undoChoice`, `makeRequest`, `sentRequests`, `requestState`, `sendUpdates`, `restart`, `tie` (used to stop the queue), `toJSON`/`fromJSON` (extra battle properties such as `rpg.pending` must serialize generically). Queue: the `'event'` action, its default order 200 and our priority 99 (mega 104 / dynamax 105 run *before* it), `resolveAction`. Pokemon: `updateMaxHp`, `getUpdatedDetails`, `baseStoredStats`/`storedStats`, `moveSlots`/`baseMoveSlots`, `set`, `cureStatus(silent)`, `heal`, `setStatus`, `removeVolatile`, `getWeight`, `isSemiInvulnerable`, `species.tags`, direct writes of `hp`/`fainted`/`status='fnt'`/`statusState` when seeding a battle from saved state, `boost()` argument convention. Format events: `onBegin`, `onFaint`, `onRpgAction`, and the `|request|` / `|error|` sideupdate text formats the gateway parses (`extractChannelMessages`). **Guard:** `experiments/step2/s5/test-engine-contract.cjs` checks that every one of these exists with the expected shape and that the staged extension files equal their sources; run it first on every bump of the pinned SHA, then the other suites.
- Content Showdown does not have (must come from our content pipeline): base exp, growth rate, EV yield, catch rate, level-up learnset in the framework's own data. The prototype uses synthetic fixtures.

**Risks (open)**
1. Engine-internal reliance above; a Showdown refactor can break the bridge silently without the suites.
2. Doubles beyond the covered combinations (multi-target throws, mega/dynamax, ally AI, simultaneous faint orders) are untested.
3. Production save is not a battle-in-progress save: engine snapshots round-trip, but a battle-time save (and recordings) is out of scope here.
4. Only Apple Silicon macOS; Windows and MZ-Deploy remain as recorded in 2.1.
5. The reference quirks in §2 are undecided.
6. Not yet shown inside MZ scenes/windows/event waits (2.4) or in a packaged build with measurements (2.5).

**Estimate (rough, AI-assisted, assumes the route is accepted; not measured)**
- 2.4 MZ flow integration (text battle UI, event wait, cancel/failure exits, save/restore): *medium* — mostly Reactor integration unknowns.
- 2.5 packaged matrix + protocol freeze: *small–medium*, plus the packaging command from the 2.1 decision.
- Beyond the prototype, per function family (a batch = rules + interface + UI + event entry + tests): the engine bridge pattern is now proven, so each family is mainly content data + rule porting + UI; exact schedule needs the scope decisions in C2. I am not giving numbers I cannot support yet.
