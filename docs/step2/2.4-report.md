Flow: map event → plugin command (`SceneManager.push`, interpreter waits) → `Scene_PSBattle` creates a `BattleSession` (the 2.3 contract, loaded through NW's Node `require` relative to `index.html`) → player acts through windows → on end the `BattleResult` is committed into `$gameSystem._psGame` (inside the MZ save data) → scene pops → the event continues (a Show Text proves it) with the outcome code in a game variable.

## Findings worth keeping

- **Showdown truncates the nickname (our stable id) to 20 characters**; ids longer than that silently stopped matching (first failure of T1). `BattleSession.create` now rejects ids that are not 1–18 chars of `A-Za-z0-9#._:-` (test added). Foe ids are `W<seq>-<n>` (unique per save because `seq` lives in the save).
- Battle ids: each `StartBattle` appends a per-save sequence number (`trainer-pidgeys#3`), so repeated encounters never collide with an already-applied battle, while a duplicate commit of the same result is still a no-op.
- Reactor's `pixi_compat` wraps scene classes; statics on the constructor are not seen through the wrapper (Reactor's own quest plugin documents this). The scene therefore carries a `_psBattle` marker and shared flow state lives on `window.PSFlow`.
- A bare `require("…")` in a Vite plugin is rewritten to a browser shim; the plugins read `require` from `globalThis` (same as 2.1).
- Synthetic `keydown`/`keyup` on `document` drive MZ's real `Input`; holding a key for ≥3 frames is needed for `isTriggered`.
- `PS_BattleSmoke` no longer auto-runs by default (`runOnBoot=false` in `js/plugins.js`) so it does not overlay the flow scenes; it still runs whenever `--ps-smoke-out` is passed.
- Persistence boundary in MZ: the commit is a synchronous in-memory replacement of `$gameSystem._psGame`; durability is MZ's own save (written by `saveGame`). Aborted battles never touch it. This boundary is **not** the atomic-file claim of 2.3 (that applies to the headless `SaveStore`); MZ save atomicity is whatever MZ/Reactor provide and was not examined here.

## Not done / limits

- Singles only in the UI; placeholder text, no art/animation/sound, no exp bar, no Pokémon summary/menus, no bag categories.
- Run/Playtest via the editor's button and a deployed package are untested for this flow (2.5). Interactive manual check: open map 4 "PS Battle Test" in MZ and playtest from there (stand next to an event, press OK); not run by me.
- Pacing delay (24 frames/line, OK skips) is untested at real speed by the scripted run (`fast=true`); behaviour with pacing on is simple but unmeasured.
- Timing/performance, memory and cold-start numbers are 2.5.
- Forced switch for the player is implemented in the scene but not exercised by a scripted scenario.
- Captured member goes to the party or boxes by size only; no nickname/receive menus.
